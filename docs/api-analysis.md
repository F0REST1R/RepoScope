# Анализ API RepoScope

## REST и RESTful

REST — архитектурный стиль: клиент и сервер разделены, запрос содержит достаточно контекста, ресурсы имеют устойчивые идентификаторы, взаимодействие использует единообразный интерфейс и допускает кэширование. RESTful API — HTTP-интерфейс, который практически следует этим ограничениям, а не просто передаёт JSON.

RepoScope моделирует существительные: `repositories`, вложенные представления `languages`, `contributors`, `issues`, `releases` и коллекцию `favorites`. Метод задаёт действие: `GET` безопасно читает, `POST` создаёт элемент коллекции, `DELETE` удаляет адресуемый ресурс. URL не содержит глаголов `get`, `add`, `remove`.

## Матрица маршрутов

| Метод | URL | Вход | Успех | Основные ошибки |
|---|---|---|---|---|
| GET | `/health` | — | 200 | — |
| GET | `/ready` | — | 200 | 503 |
| GET | `/rate-limit` | headers GitHub внутри backend | 200 | 429, 502 |
| GET | `/repositories/search` | `q`, `language`, `sort`, `order`, `page`, `per_page` | 200 | 422, 429, 502 |
| GET | `/repositories/{owner}/{repo}` | path | 200 | 404, 422, 429 |
| GET | `…/languages` | path | 200 | 404, 429 |
| GET | `…/contributors` | path + pagination | 200 | 404, 422, 429 |
| GET | `…/issues` | path + pagination | 200 | 404, 422, 429 |
| GET | `…/releases` | path + pagination | 200 | 404, 422, 429 |
| GET | `/favorites` | — | 200 | 500 |
| POST | `/favorites` | JSON `{owner,repo}` | 201 + Location | 400, 404, 409, 422, 429, 500 |
| DELETE | `/favorites/{owner}/{repo}` | path | 204 | 404, 422, 500 |

## Семантика и идемпотентность

`GET` не меняет состояние и может кэшироваться. `DELETE` идемпотентен по смыслу: после первого успешного вызова ресурс отсутствует; повторный вызов возвращает диагностический `404`. `POST` не идемпотентен как метод, но уникальное ограничение не допускает две одинаковые записи и сообщает `409 Conflict`.

`201 Created` сопровождается `Location`. При `204` тело отсутствует. `400` зарезервирован для синтаксически неверного JSON, `422` — для понятного JSON/URL с неверными значениями, `404` — для отсутствия ресурса, `409` — для конфликта текущего состояния.

## Ошибки

```json
{
  "error": {
    "code": "validation_error",
    "message": "Параметр q должен содержать от 2 до 256 символов",
    "request_id": "m1abc-2",
    "details": {"q": "invalid"}
  }
}
```

`code` предназначен для программы, `message` — для человека, `request_id` связывает ответ со структурированным логом, `details` даёт контекст. Внутренние SQL/сетевые ошибки не раскрываются клиенту.

## Пагинация и ограничения upstream

`page` и `per_page` ограничены диапазоном 1–100. Поиск GitHub фактически ограничивает доступную выборку первой тысячей результатов, поэтому `total_pages` ограничен 100 при `per_page=10` и в целом не обещает обход всего `total_count`. Для списков `has_next` вычисляется по заполненности страницы; это практичный компромисс без дополнительного запроса.

GitHub может вернуть `403` или `429` при primary/secondary rate limit. RepoScope отвечает `429 github_rate_limited`; возможный `Retry-After` находится в `details`. Текущие buckets видны через `/rate-limit`.

## Соответствие контракту

Источником машиночитаемого контракта служит [`openapi.yaml`](openapi.yaml). При изменении маршрута обязательны синхронные изменения handler-теста, OpenAPI, Postman и cURL. Интеграционные тесты проверяют заголовки, статусы и основной lifecycle; Postman проверяет контракт на работающем стенде.
